# Hof — архитектура первой версии

Статус: фазы 1–6 утверждены. 2026-10-05 — Phase 2 (архитектура), Phase 3 (модель данных, раздел 5), Phase 4 (UX, раздел 6). 2026-10-08 — Phase 5 (визуальный язык, раздел 6) и Phase 6 (HTTP и безопасность, раздел 4). Документ описывает только первую версию; то, что не нужно для [PRODUCT.md](PRODUCT.md), здесь не проектируется.

## 1. Обзор

```
Браузер
   │  HTTPS
   ▼
nginx ─────────── TLS, редирект с HTTP на HTTPS, лимит попыток входа, проксирование
   │  HTTP, внутренняя сеть Docker
   ▼
hof (Node.js, один процесс)
   ├── Core   — /, /setup, /login, /logout, /account, /admin/…
   └── Säckel — /saeckel/…
   │
   ▼
PostgreSQL (одна база)
   ├── схема core    — владелец роль hof_core
   └── схема saeckel — владелец роль hof_saeckel
```

Три контейнера: `nginx`, `hof`, `postgres`. Снаружи доступен только `nginx`.

Core и Säckel работают в одном процессе, но остаются отдельными модулями: у каждого свой код, свои маршруты, свой интерфейс и свои данные. Один процесс — это способ запуска, а не отказ от границ (раздел 2).

Почему не отдельный процесс на приложение: отдельные процессы нужны для независимой установки, перезапуска и обновления приложений. Это задачи второго приложения и установщика, которых в первой версии нет. От текущей границы (раздел 2) требуется только одно: не мешать разделению, если оно когда-нибудь понадобится. Само разделение не проектируется и не считается обязательным.

## 2. Граница Core ↔ Säckel

**Код.** `src/core/` и `src/saeckel/` не импортируют друг друга. Это проверяет правило lint. Оба модуля знает только точка сборки `src/main.ts`.

**Контракт.** Säckel получает от Core ровно одно — функцию, которую `main.ts` передаёт ему при старте:

```
currentUser(request) → { id, username } или null
```

Плюс четыре URL-адреса: `/` (главная Hof, «← Двор»), `/login` (куда отправить без входа), `/static/fx-head.js` и `/static/fx.js` (эффекты, раздел 6). Больше Säckel о Core ничего не знает. Общие проверки запроса (Origin, тело, заголовки ответа) делает `main.ts` до обоих модулей (раздел 4).

Core о Säckel не знает ничего. Список приложений для главной страницы — константа в `main.ts` (сейчас один элемент: название и путь Säckel). Это не registry.

**Данные.** У каждого модуля своя схема в PostgreSQL и своя роль БД. Роль Säckel не имеет прав на схему `core`, и наоборот. Запрет «залезть в чужие таблицы» обеспечивает сама база, а не дисциплина. Säckel хранит id владельца данных как обычное значение, без внешнего ключа на таблицы Core.

## 3. Как проходит запрос

Пример: пользователь записывает трату в Säckel.

1. Браузер отправляет форму `POST /saeckel/…` вместе с cookie сессии.
2. `nginx` проксирует запрос в `hof`.
3. `main.ts` проверяет `Origin` и размер тела (раздел 4).
4. Middleware Säckel вызывает `currentUser(request)`. Core находит сессию в своей схеме и проверяет срок и что пользователь не отключён. Если получен `null`, ответ — редирект на `/login`.
5. Обработчик Säckel разбирает и проверяет поля формы. При ошибке он заново показывает ту же страницу со статусом 400, сообщениями и введёнными значениями.
6. SQL выполняется через пул БД Säckel. Каждый запрос к данным бюджета ограничен `user_id` текущего пользователя — так обеспечивается «личный бюджет». Запись денег идёт под блокировкой строки мешка (раздел 4.8).
7. Ответ — 303 на страницу Säckel (POST → redirect → GET), браузер показывает новые остатки.

Неожиданная ошибка попадает в общий обработчик модуля: стек пишется в лог сервера, пользователь видит страницу «что-то пошло не так» без деталей.

Внутри модуля не больше двух уровней: HTTP-обработчик (разбор, проверка, авторизация, ответ) и функции с SQL. Слоёв service/repository/use-case нет. Бизнес-правила, которые стоит тестировать отдельно от HTTP (например, разбор суммы), — обычные функции.

## 4. HTTP и безопасность

- **Сессии на сервере.** При входе сервер создаёт случайный токен и отдаёт его в HttpOnly cookie, а в базе хранит только хеш токена. Каждый запрос ищет сессию в базе. Отозвать сессию значит удалить строку, и это действует сразу. Так выполняется требование «отключённый пользователь сразу теряет доступ».
- **Один origin.** Core и Säckel работают на одном домене и различаются путём (`/saeckel/`), поэтому одна cookie действует для обоих. Это и есть единый вход, без отдельного SSO.
- **Общие проверки — в `main.ts`**, до маршрутов обоих модулей: `Origin` (4.6), тело запроса (4.7), заголовки ответа (4.9). Säckel для них ничего не получает от Core.

Почему не JWT: мгновенно отозвать JWT без проверки в базе нельзя, а с проверкой в базе он ничего не добавляет к обычной сессии.

Почему не отдельный identity provider (OIDC и т. п.): он решает вход в приложения на разных доменах и серверах. Здесь один домен и один процесс.

### 4.1 Маршруты

- Только HTML-формы, методы GET и POST. GET ничего не меняет. Успешный POST отвечает 303 на GET; `Location` — всегда относительный путь.
- Форма отправляется на адрес своей страницы. Если на странице несколько форм, у каждой свой путь действия.
- Ошибка формы — та же страница со статусом 400. Введённые значения сохраняются, кроме паролей.
- Сообщение после редиректа — флаг из белого списка (`?done=password`) или id своей записи (`?created=7`, `?fresh=345`). Текст сообщения собирает сервер, из адреса он не берётся. Неизвестный флаг и чужой id игнорируются.
- Пока Хозяина нет, любой путь, кроме static, отвечает 303 на `/setup`. Другие методы и неизвестные пути — 404.

### 4.2 Сессии

- Токен — 32 случайных байта (`randomBytes`) в base64url, 43 символа. В `sessions.token_hash` лежит SHA-256 строки cookie, без соли: токен случайный, перебирать нечего. Значение cookie не из 43 символов `[A-Za-z0-9_-]` считается отсутствием сессии, запрос в БД не идёт.
- Cookie: `__Host-hof=<token>; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=2592000`. Префикс `__Host-` не даёт соседнему поддомену подложить или перезаписать cookie. `Secure` всегда, флага в конфигурации нет: Chrome считает http://localhost безопасным, остальные браузеры для разработки проверяются в первом milestone. `Lax`, а не `Strict`: ссылка на Hof из мессенджера не должна вести на вход при живой сессии.
- Срок — 30 дней от входа, абсолютный, без продления и без idle-таймаута. На каждом запросе в БД ничего не пишется. Просроченные строки удаляются при каждом успешном входе.
- `currentUser` — один запрос: сессия по `token_hash`, `expires_at > now()`, пользователь не отключён.
- Токен всегда создаёт сервер в момент аутентификации; значение от клиента сессией не становится никогда, поэтому session fixation исключена.

| Событие | Сессии | Cookie |
|---|---|---|
| вход, основание двора | сессия из старой cookie удаляется, создаётся новая | новый токен |
| выход | удаляется текущая | стирается (`Max-Age=0`) |
| смена своего пароля | удаляются все сессии пользователя, создаётся новая для этого устройства | новый токен |
| сброс пароля (Хозяин, CLI), «Забрать ключ» | удаляются все сессии пользователя | — |
| «Вернуть ключ» | без изменений: сессий нет, человек входит заново | — |

Транзакции этих событий — 4.8.

### 4.3 Пароли

- 15–256 символов (кодовых точек) после нормализации NFKC. Пробелы не обрезаются, допустимы любые символы, правил состава и принудительной смены нет. Минимум действует для всех новых паролей (основание, смена своего, начальный, сброс, CLI); при входе проверяется только максимум. NFKC нужен, потому что один и тот же пароль с «ё» или «й» с разных устройств может прийти в разной Unicode-форме.
- Argon2id из `node:crypto`, асинхронный вызов: синхронный блокировал бы сервер. Один профиль для всех установок: `m=19456` KiB, `t=2`, `p=1`, соль 16 случайных байт, хеш 32 байта. Подбора параметров при старте нет.
- `password_hash` — PHC-строка `$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>` (base64 без `=`). Проверка берёт параметры из строки, поэтому профиль можно будет усилить, не ломая старые хеши. Сравнение — `timingSafeEqual`.
- Если строка не разбирается, алгоритм не `argon2id`, версия не 19 или параметры выше `m=262144`, `t=10`, `p=4`, вход не удаётся с общей ошибкой, а в лог пишется `password_hash_unreadable` с id пользователя, без хеша. Это не 500; доступ возвращают сбросом пароля.
- Для неизвестного логина Argon2 считается против фиктивного хеша, созданного при старте с тем же профилем. По времени ответа не понять, существует ли логин.
- **Восстановление доступа** — команда на сервере: `docker compose exec hof node src/cli.ts reset-password <логин>`. Она дважды спрашивает новый пароль без эха; аргументом и через переменную окружения пароль не передаётся. Если stdin не терминал, команда отказывается работать. Правила пароля те же, все сессии пользователя удаляются.

### 4.4 Первый запуск

- Пока в базе нет Хозяина, сервер при старте пишет в лог «Ключ от ворот»: 20 символов Crockford base32 (без I, L, O, U) группами `XXXXX-XXXXX-XXXXX-XXXXX`, 100 бит. При вводе регистр, пробелы и дефисы игнорируются; сравнение — SHA-256 обоих значений и `timingSafeEqual`.
- Ключ живёт только в памяти процесса: до основания двора или остановки процесса. После перезапуска — новый ключ, старый недействителен. Таймера нет: 100 бит онлайн не перебрать.
- Argon2 запускается только после верного ключа. Неверная попытка пишется в лог как warn, без введённого значения. Лимит попыток — только nginx по IP (4.5). Глобальной блокировки нет, чтобы посторонний не мог сорвать установку.
- Основание — одна транзакция: Хозяин и его сессия. Две одновременные отправки с верным ключом разрешает частичный UNIQUE «один администратор» (5.2): вторая получает ошибку уникальности и 303 на `/`.
- После основания ключ обнуляется, `GET /setup` отвечает 404, а `POST /setup` — 303 на `/` без проверок и записи. Признак «Хозяин есть» после первого `true` запоминается в памяти: удалить или отключить Хозяина нельзя.

### 4.5 Перебор паролей

- nginx ограничивает по IP одной зоной `POST /login`, `POST /setup` и `POST /account/password`: 10 запросов в минуту, всплеск 10, ответ 429. Это же защищает CPU: каждая попытка стоит одного вычисления Argon2.
- Блокировки по логину в приложении нет. Она позволяла бы постороннему, знающему логин, закрыть человеку вход и выдавала бы существование логина через 429. Распределённый перебор одного логина сдерживает длина пароля.

### 4.6 CSRF, права, возврат после входа

- **CSRF:** cookie `SameSite=Lax` и обязательная проверка `Origin` для всех методов, кроме GET и HEAD. Допустим только `Origin`, равный `https://` + `Host`. Если `Host` — `localhost` или `localhost:<порт>`, допустим ещё `http://` + `Host` (разработка). Нет заголовка, `null`, другая схема, хост или порт — 403 и warn в лог. Флага режима нет: через nginx `Host` всегда равен домену (чужие сбрасываются, раздел 9), а cookie Hof к запросу на `localhost` браузер не приложит. CSRF-токенов нет: схема держится на том, что GET ничего не меняет, а выход — только POST.
- `Referrer-Policy` — только `same-origin` (4.9): при `no-referrer` браузеры отправляют на POST `Origin: null`, и формы перестанут работать.

| Кто | Доступно | Остальное |
|---|---|---|
| Хозяина ещё нет | `/setup`, static | 303 `/setup` |
| не вошёл | `/login`, `POST /logout`, static | GET → 303 `/login?next=…`; POST → 303 `/login` |
| пользователь | `/`, `/account…`, `/logout`, `/saeckel/…` | `/admin/…` → 403 «Сюда только хозяину» |
| Хозяин | всё | `/admin/users/<свой id>` → 404: свой пароль меняется в «Моих покоях» |

- Роль — флаг `is_admin`. Обработчики `/admin/…` проверяют его сами и до поиска записи, поэтому 403 не выдаёт, существует ли пользователь.
- Данные Säckel: в каждом SQL условие на `user_id` текущего пользователя. Чужая и несуществующая запись одинаково дают 404. Чужой id мешка в поле формы даёт 400 «Мешок не найден», как и несуществующий. Составные FK (5.5) — вторая линия.
- **Возврат после входа.** Без сессии GET отвечает 303 на `/login?next=<путь и query>`; POST — 303 на `/login` без `next`. `next` принимается, только если начинается с `/`, второй символ — не `/` и не `\`, все символы — печатные ASCII от `!` до `~` без `\`, длина — до 512. Иначе — `/`. Так абсолютный URL невозможен: `//host` и `/\host` отсечены, а пробелы и управляющие символы, которые браузер вырезал бы, запрещены.

### 4.7 Проверка ввода

- Любое значение из формы, query или пути — строка. Его разбирает явная функция и возвращает значение нужного типа или текст ошибки; библиотеки схем нет. В SQL только параметры `$1…`; ORDER BY и LIMIT — константы в коде.
- Длина считается в кодовых точках (`[...s].length`), как `char_length` в PostgreSQL. Текст нормализуется в NFC и обрезается по краям. Управляющие символы U+0000–U+001F и U+007F отклоняются: `\0` PostgreSQL не принимает.
- CHECK в БД — вторая линия. Если CHECK сработал на вводе, это ошибка валидации: 500 и запись в лог. Ожидаемые нарушения уникальности (имя мешка, логин, второй Хозяин) — обычная ошибка формы.

| Поле | Правило |
|---|---|
| логин | обрезка, нижний регистр, `^[a-z0-9][a-z0-9._-]{0,31}$`; при входе неверный формат — та же общая ошибка |
| пароль | 4.3; повтор должен совпасть |
| ключ от ворот | без пробелов и дефисов, верхний регистр, ровно 20 символов алфавита |
| имя мешка | 1–50 символов; уникальность среди активных проверяет БД |
| знак мешка | ключ из набора в коде Säckel |
| заметка | 0–200 символов, одна строка |
| сумма | до 20 символов: цифры; разделители групп — пробел, U+00A0, U+202F; один `,` или `.` и не больше двух знаков после него; без знака и экспоненты; от 0,01 до 1 000 000 000,00. Принимается всё, что печатает сам Hof |
| дата | `ДД.ММ.ГГГГ` или `ГГГГ-ММ-ДД`, существующая дата от 01.01.2000 до сегодня + 1 год; по умолчанию сегодня (`TZ`) |
| id в пути, форме, query | `^[1-9][0-9]{0,9}$` и не больше 2 147 483 647; иначе 404 (путь) или 400 (форма) |
| `page` | 1–1000; иначе 404 |
| `done`, `created`, `fresh`, `income`, предзаполнение | белый список или id своей записи; иначе игнорируется |

- Тело POST — только `application/x-www-form-urlencoded`, иначе 415: загрузки файлов нет. Размер — не больше 16 KiB (`bodyLimit` из Hono), иначе 413. Лишние поля игнорируются.

### 4.8 Транзакции и одновременные запросы

Уровень изоляции — READ COMMITTED по умолчанию. Инварианты держат блокировки строк; SERIALIZABLE, повторов и advisory locks нет.

- **Пароль и сессии.** Argon2 считается вне транзакции, против хеша, прочитанного до проверки. Вход и смена своего пароля затем идут одной транзакцией: `SELECT password_hash, is_disabled FROM users … FOR UPDATE`; если хеш изменился или пользователь отключён — отказ; при смене — `UPDATE` хеша и удаление всех сессий; создание сессии; COMMIT. Сброс пароля (Хозяин, CLI) и «Забрать ключ»: **сначала** `UPDATE users`, **потом** удаление сессий, COMMIT. При обратном порядке удаление не увидело бы сессию незакоммиченного входа. Так вход старым паролем не переживает сброс, а смена по старому паролю не затирает сброс.
- **Мешки.** Деньги и архивность мешка меняются только под блокировкой его строки. Создание операции блокирует её мешки: `SELECT … FROM pouches WHERE user_id = … AND id = ANY(…) ORDER BY id FOR UPDATE`; если мешок не найден или в Кладовой — отказ. Правка и удаление сначала блокируют саму операцию (`SELECT … FROM operations … FOR UPDATE`; нет — 404), затем тем же запросом её актуальные старые и новые мешки. Архивация блокирует мешок, затем отдельным запросом считает остаток; не ноль — отказ. Блокировка от внешнего ключа не помогает: она не конфликтует с `UPDATE is_archived`. Порядок везде один — операция, затем мешки по возрастанию id, поэтому взаимоблокировок нет. Доход мешков не касается. Восстановление и переименование — один `UPDATE`, конфликт имён ловит частичный UNIQUE.
- **«Разложить»** — все строки одной транзакцией под блокировками всех мешков: ошибка в любой строке — не пишется ничего.
- **Одна операция из двух вкладок** — побеждает последняя запись. Если запись уже удалена, правка получает 404.
- **Основание двора** — 4.4. **Отключение во время входа** — сессию отсекает проверка `is_disabled` в `currentUser`.
- **Повторная отправка формы**, когда ответ потерялся после записи, может создать вторую операцию. Риск принят: случай редкий, лишняя строка сразу видна подсвеченной и удаляется. `fx.js` гасит двойное нажатие. Вопрос пересматривается после 4 недель реального использования; если дубли появятся — скрытый одноразовый ключ формы и UNIQUE в `operations`.

### 4.9 Заголовки ответа

Ставятся в `main.ts` явными строками, без готового набора Hono:

```
Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; media-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: same-origin
Cache-Control: no-store            (только HTML)
```

- В шаблонах нет inline-скриптов и атрибутов `style`: координаты и размеры задаются классами в CSS. `fx.js` меняет стили через CSSOM — это CSP не запрещает. `<audio>` и Web Audio поверх него работают через `media-src`. Шрифты, картинки и звуки — только свои файлы.
- XSS: подставленные значения экранирует шаблон `html`; `raw()` для пользовательских данных запрещён.
- `no-store` уменьшает вероятность, что «Назад» после выхода покажет страницу из кэша, но не гарантирует этого: у браузеров свой back/forward cache. Выход и «Назад» проверяются интеграционно в актуальных Chrome, Firefox и Safari (компьютер и iOS).
- HSTS ставит nginx (раздел 9).

### 4.10 Логи

- stdout, одна строка на событие: `level event key=value`.
- Пишутся: старт (порт, применённые миграции); ошибка миграции перед выходом; ключ от ворот — только в сообщении при старте; основание двора; вход (логин, IP); неудачный вход (логин и IP, если логин существует, иначе только `unknown_user`: в поле логина люди вводят пароль); отказ по `Origin`; смена и сброс пароля; действия Хозяина (кто, что, с кем); неожиданная ошибка (стек, метод, путь).
- Не пишутся никогда: пароли и любые поля паролей, токен, заголовки `Cookie` и `Set-Cookie`, введённые значения ключа, хеши паролей, тела запросов (суммы и заметки — частный бюджет), пароли БД и содержимое `.env`.
- IP берётся из `X-Real-IP`, который nginx всегда перезаписывает. Он нужен только для логов; решения по нему не принимаются.

## 5. Данные

- PostgreSQL 18, одна база `hof`, схемы `core` и `saeckel`, роли `hof_core` и `hof_saeckel`. Роли и схемы создаёт скрипт инициализации контейнера `postgres` при первом создании базы.
- Сервер держит два пула соединений: Core работает под своей ролью, Säckel — под своей.
- SQL пишется вручную, только с параметрами (`$1`, `$2`, …). ORM и query builder нет.
- **Миграции** — пронумерованные `.sql`-файлы в `src/<модуль>/migrations/`. Сервер применяет их при старте, до приёма запросов: каждую в отдельной транзакции и под ролью своего модуля. Учёт ведётся в таблице `schema_migrations` в схеме модуля. Миграции идут только вперёд. Откат — восстановление из резервной копии, сделанной перед обновлением.
### 5.1 Модель данных

```
 схема core                           схема saeckel

 ┌──────────┐      ┌──────────┐      ┌───────────┐       ┌────────────┐
 │ users    │◄─FK──│ sessions │      │ pouches   │◄─FK───│ operations │
 └──────────┘      └──────────┘      └───────────┘       └────────────┘
      ▲                                    ┆                   ┆
      └┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┴┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┘
          user_id — только значение, без внешнего ключа
```

Четыре таблицы, по две у каждого модуля. Säckel хранит `user_id` как обычное значение: роль `hof_saeckel` не видит схему `core`, поэтому внешний ключ на `core.users` невозможен и не нужен. Пользователей не удаляют, только отключают, поэтому висячих ссылок не возникает.

### 5.2 `core.users` — аккаунты

Зачем: кто может войти и кто администратор. Владелец: Core.

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | `integer`, identity | PK |
| `username` | `text` | NOT NULL, UNIQUE; CHECK: только `a-z`, `0-9`, `.`, `_`, `-`, первый символ — буква или цифра, до 32 символов |
| `password_hash` | `text` | NOT NULL; одна строка: алгоритм, параметры, соль, хеш |
| `is_admin` | `boolean` | NOT NULL, по умолчанию false |
| `is_disabled` | `boolean` | NOT NULL, по умолчанию false |

Инварианты:

- Логин уникален. CHECK пропускает только нижний регистр, а приложение приводит ввод к нижнему регистру, поэтому `Anna` и `anna` — один и тот же логин.
- Администратор не больше одного: частичный UNIQUE-индекс по `is_admin` для строк с `is_admin = true`. Этот же индекс разрешает гонку при двух одновременных отправках формы первого запуска: вторая получает ошибку уникальности.
- Администратора нельзя отключить: CHECK `NOT (is_admin AND is_disabled)`.
- «Первый запуск выполнен» означает «администратор существует». Отдельного флага нет.

Индексы: PK, UNIQUE по `username` и индекс «один администратор». Других не нужно.

### 5.3 `core.sessions` — активные входы

Зачем: сессии на сервере (раздел 4). Владелец: Core.

| Поле | Тип | Ограничения |
|---|---|---|
| `token_hash` | `bytea` | PK; SHA-256 токена из cookie. Сам токен нигде не хранится |
| `user_id` | `integer` | NOT NULL, FK → `users.id` |
| `expires_at` | `timestamptz` | NOT NULL; вход + 30 дней |

Инварианты:

- Сессия действительна, только если `expires_at` ещё не наступил и пользователь не отключён. Это проверяется при каждом запросе.
- Отозвать сессию значит удалить строку. Просроченные строки удаляются при входе; планировщика нет.
- Срок абсолютный, без продления (раздел 4.2), поэтому `expires_at` достаточно: время создания не хранится.

Индексы: PK (поиск по токену на каждом запросе) и `user_id` (завершение всех сессий пользователя при отключении, сбросе или смене пароля).

### 5.4 `saeckel.pouches` — мешки

Зачем: категории, по которым распределяются деньги. Владелец: Säckel.

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | `integer`, identity | PK |
| `user_id` | `integer` | NOT NULL |
| `name` | `text` | NOT NULL; CHECK: без пробелов по краям, от 1 до 50 символов |
| `icon` | `text` | NOT NULL, по умолчанию `'pouch'` |
| `is_archived` | `boolean` | NOT NULL, по умолчанию false |

Инварианты:

- Мешок принадлежит одному пользователю, `user_id` не меняется.
- Среди неархивных мешков пользователя имена уникальны без учёта регистра: частичный UNIQUE по `(user_id, lower(name))` для строк с `is_archived = false`.
- UNIQUE `(id, user_id)` нужен как цель составных внешних ключей из `operations`.
- `icon` — ключ знака из набора, который задан в коде Säckel. Форма принимает только ключи из набора. CHECK в базе не ставится: набор будет пополняться, а миграция ради картинки лишняя. Неизвестный ключ показывается как мешок.
- Мешки не удаляются, только архивируются. Архивный мешок можно восстановить. Если его имя уже занято активным мешком, восстановление отклоняется с понятным сообщением (это срабатывает частичный UNIQUE выше).
- Правила, которые проверяет приложение, потому что остаток вычисляется и ограничением его не выразить:
  - архивировать можно только мешок с нулевым остатком;
  - пока мешок в архиве, операции с ним нельзя создавать, исправлять и удалять. Чтобы исправить старую историю, мешок восстанавливают, исправляют операции, при необходимости приводят остаток к нулю и архивируют снова.

Индексы: только перечисленные. У одного пользователя десятки мешков.

### 5.5 `saeckel.operations` — движение денег

Зачем: вся история бюджета, из неё считаются остатки. Владелец: Säckel.

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | `integer`, identity | PK |
| `user_id` | `integer` | NOT NULL |
| `kind` | `text` | NOT NULL; CHECK: `income`, `assign`, `expense` или `transfer` |
| `amount` | `bigint` | NOT NULL; в сотых долях валюты; CHECK: от 1 до 100 000 000 000 |
| `currency` | `text` | NOT NULL; CHECK: `^[A-Z]{3}$`; валюта установки на момент записи (5.6) |
| `from_pouch_id` | `integer` | NULL |
| `to_pouch_id` | `integer` | NULL |
| `date` | `date` | NOT NULL; календарная дата без времени |
| `note` | `text` | NOT NULL, по умолчанию `''`; CHECK: до 200 символов |

Какие мешки заполнены, зависит от `kind`; это тоже проверяет CHECK:

| `kind` | from | to | Смысл |
|---|---|---|---|
| `income` | — | — | доход → «Нераспределено» |
| `assign` | — | мешок | «Нераспределено» → мешок |
| `expense` | мешок | — | трата из мешка |
| `transfer` | мешок | другой мешок | перенос между мешками |

Инварианты:

- Сумма всегда положительна, направление задаёт `kind`.
- `currency` во всех строках одна и та же — валюта установки. Это не мультивалютность, а единица, в которой записана сумма; при старте сервер проверяет, что она совпадает с `CURRENCY` (5.6).
- У `transfer` исходный и целевой мешки различаются: CHECK `from_pouch_id <> to_pouch_id`.
- Операция ссылается только на мешки своего пользователя: составные FK `(from_pouch_id, user_id)` и `(to_pouch_id, user_id)` → `pouches (id, user_id)`. Даже ошибка в коде не позволит записать трату в чужой мешок.
- При редактировании `kind` не меняется. Чтобы сменить вид операции, её удаляют и создают заново (правило приложения).
- Верхняя граница `amount` ограничивает только одну операцию и отсекает явно ошибочный ввод. Безопасный диапазон итогов по всей истории она сама по себе не гарантирует. Поэтому агрегаты всегда проверяются при чтении (раздел 5.6).

Индексы: PK и `(user_id, date, id)` — для истории пользователя по датам и для выборки его операций при подсчёте остатков.

### 5.6 Остатки, деньги, даты

- Остатки вычисляются, а не хранятся:
  - остаток мешка = Σ `assign` в него + Σ `transfer` в него − Σ `expense` из него − Σ `transfer` из него;
  - «Нераспределено» = Σ `income` − Σ `assign`.

  Это один SQL-запрос при показе страницы. У одного пользователя порядка тысячи операций в год, поэтому хранить остатки и синхронизировать их не нужно.
- Остатки могут быть отрицательными: перерасход в мешке или распределено больше, чем пришло. БД их не ограничивает, интерфейс показывает минус явно. Запрещать минус при создании операции бессмысленно: правка или удаление старой операции всё равно может к нему привести.
- Суммы — целые числа в сотых долях. `pg` отдаёт `bigint` и результаты `SUM` строками, поэтому при чтении они явно преобразуются в `number` с проверкой `Number.isSafeInteger`. Если проверка не проходит, это ошибка сервера с записью в лог, а не тихо неверное число.
- **Валюта** одна на всю установку и задаётся в конфигурации развёртывания: `CURRENCY` в `.env` (код ISO 4217, например `RUB` или `EUR`). Мультивалютности нет. Первый релиз поддерживает только валюты с двумя знаками после запятой. При старте сервер проверяет код встроенными средствами: он должен быть в `Intl.supportedValuesOf('currency')`, а `Intl.NumberFormat` должен давать для него ровно два знака после запятой. Иначе сервер завершается с понятной ошибкой. Через `Intl.NumberFormat` же форматируются суммы.
- Каждая операция записывается с `currency = CURRENCY`. При старте, до приёма запросов, Säckel ищет операцию с другой валютой. Если она есть, сервер завершается с ошибкой вида «в .env CURRENCY=EUR, а записи Säckel в RUB; смена валюты не поддерживается». Пока операций нет, ошибочное значение исправляется правкой `.env`; после первой операции валюта установки зафиксирована. Так смена `CURRENCY` не может тихо изменить смысл сумм.
- «Сегодня» для даты по умолчанию считается в часовом поясе сервера (`TZ` в `.env`).
- Одновременные запросы и блокировки — раздел 4.8. Если одну операцию правят из двух вкладок, побеждает последняя запись.

### 5.7 Миграции

| Файл | Что создаёт |
|---|---|
| `src/core/migrations/001_users.sql` | `users`, его ограничения и индексы |
| `src/core/migrations/002_sessions.sql` | `sessions` и индекс по `user_id` |
| `src/saeckel/migrations/001_pouches.sql` | `pouches`, его ограничения и индексы |
| `src/saeckel/migrations/002_operations.sql` | `operations`, его ограничения и индекс |

Схемы, роли и права — не миграции: их один раз создаёт `deploy/postgres-init.sh`. У каждой роли `search_path` указывает на её схему, поэтому в SQL имена таблиц пишутся без префикса. Таблицу `schema_migrations` создаёт `migrate.ts` при первом запуске.

### 5.8 Чего в модели нет

- `installed_applications`: список приложений — константа в `main.ts`.
- Таблицы состояния первого запуска: оно выводится из наличия администратора, а код установки живёт только в памяти процесса.
- `settings`: настроек нет.
- `budgets`: личный бюджет — это строки с `user_id` пользователя. Общий бюджет, если понадобится, проектируется отдельно и потребует миграции. Это осознанное решение.
- Счетов, периодов, целей, долгов, таблицы валют (валюта установки — в конфигурации и в каждой операции, раздел 5.6); цветов и порядка мешков; имени и email пользователя; журнала действий; полей `created_at`/`updated_at` «на всякий случай»; мягкого удаления операций.

## 6. Интерфейс

- HTML формирует сервер: шаблоны — функции на TypeScript с тегом `html` из Hono, который экранирует подставленные значения. Браузер отправляет обычные HTML-формы.
- Нет клиентского фреймворка, сборщика, клиентского состояния и JSON API.
- У Core и у Säckel свой CSS-файл и свой шаблон страницы. Общий визуальный язык держится на одинаковых значениях (цвета, шрифты, отступы), которые копируются, а не выносятся в общий пакет.
- JavaScript — только файлы эффектов `fx-head.js` и `fx.js` (подраздел «Анимации, звуки и музыка»). Без них всё работает: формы, ссылки и переходы обычные.
- Цена такого выбора: после каждого действия страница перезагружается. Если пропала сеть, браузер показывает свою страницу ошибки, а не сообщение приложения.
- Phase 5 подтвердила: утверждённый UI не требует SPA, HTML на сервере остаётся. React «на будущее» не добавляется.

### UX первой версии

- **Принципы.** Hof — не dashboard: на главной только приложения. Результат действия виден сразу на той же странице (новый остаток, новая строка). У экрана одно главное действие, навигация не глубже двух уровней. Ошибка ввода показывается в той же форме, введённые значения сохраняются. Чужие и несуществующие записи дают 404. Загрузка — обычная загрузка страницы браузером, отдельного loading UI нет.
- **Навигация Hof:** Двор (службы) · Мои покои (пароль, выход) · Приближённые (только Хозяин). Кто не вошёл, попадает на Вход и после него возвращается туда, куда шёл. Пока Хозяина нет, любой адрес ведёт на Основание двора.
- **Навигация Säckel:** Мешки · Летопись, ссылка «← Двор». С экрана Мешки: мешок, доход, раскладка из Казны, перекладывание, новый мешок и свёрнутая Кладовая.
- **Ключевые flows:**
  1. Трата: Мешки → мешок → сумма → «Записать» → та же страница с новым остатком. Общей кнопки «+ Трата» нет.
  2. Доход: деньги попадают в Казну, после записи открывается «Разложить по мешкам». Раскладывать не обязательно: можно вернуться к Мешкам и оставить деньги в Казне.
  3. Мешок в долгу: показывает минус и ссылку «Покрыть из другого мешка», которая открывает «Переложить» с заполненными «куда» и суммой.
  4. Исправление: Летопись → операция → исправить или удалить с подтверждением.
  5. Кладовая: правила архива из раздела 5.4. Вернуть мешок можно из свёрнутой Кладовой на экране Мешки.
  6. Приближённые: Хозяин принимает человека ко двору с начальным паролем, который задаёт сам и передаёт человеку. Обязательной смены пароля нет. Сброс пароля и «Забрать ключ» (отключение) завершают сессии пользователя.
- Повторная отправка формы, когда ответ потерялся, — принятый риск (раздел 4.8). После каждой записи — POST → redirect → GET.
- **Словарь.** Стилизуются названия, заголовки, подсказки и кнопки, если смысл не теряется. Поля форм и ошибки ввода остаются простыми (Логин, Пароль, Сумма, Дата, Заметка).

  | Понятие | В интерфейсе |
  |---|---|
  | главная, приложения | Двор, Службы двора |
  | администратор, пользователи | Хозяин, Приближённые |
  | аккаунт, выйти | Мои покои, Покинуть двор |
  | вход, первый запуск | «Войти во двор»; Основание двора, код установки — «Ключ от ворот» |
  | создать, отключить, включить пользователя | Принять ко двору, Забрать ключ, Вернуть ключ |
  | пользователь включён, отключён | С ключом, Ключ взят |
  | нераспределённые деньги | Казна |
  | распределить, перенести | Разложить по мешкам, Переложить |
  | история, архив мешков | Летопись, Кладовая |
  | перерасход | В долгу |
  | ошибки 404, 403, 500 | «Такой тропы во дворе нет», «Сюда только хозяину», «Во дворе что-то стряслось» |

  Без изменений: Мешок, Доход, Трата, начальный пароль.

### Визуальный язык

- **Принцип.** Мир Hof — двор замка. Каждый экран — своё место во дворе: вход — ворота, главная — двор, Приближённые — сторожка, Мои покои — комната, сервис — своё место или предмет. Стилизация полная: мир живёт в знаке, иллюстрациях, языке (словарь выше) и материалах интерфейса — меню-знамя, ленты заголовков, рамки пером, вывески, ключи. Предмет на экране и есть данные: ключ — доступ человека, мешок — статья бюджета, сундук — Казна. Элементы управления остаются привычными: поле — поле, кнопка — кнопка, меняется только их линия.
- **Иллюстрации:** у каждого места своя композиция, а не одна полоса на всех (вход — сцена на весь экран, Двор — карта с вывесками-ссылками, Приближённые — картина сбоку во всю высоту, Säckel — сцена сверху с названием на ленте); эмблемы в меню; виньетки пустых состояний и ошибок. Сцены рисуются до краёв, текст лежит только на ленте, вывеске или бумаге, кадры для компьютера и телефона свои. Стиль: синие чернила и штриховка по бумаге; снаружи тепло точечно, в комнатах дерево и латунь теплее; сквозной персонаж — один и тот же кот. Исходники лежат в `design/generated/`, карта мира, генерация и обработка описаны в `design/asset-prompt.txt`. Это статичные WebP-файлы, JavaScript для них не нужен.
- **Знак Hof** — `design/logo/hof-mark.svg`, подпись «Ваш личный двор».
- **Цвета** — в `design/screens.css`: тёплая бумага с плиткой и пятнами тона, синие чернила, синий Hof, красный для ошибок и минуса; у Säckel акцент — охра.
- **Шрифт** — EB Garamond, одна семья, чтобы не было смеси: прямой — для всего, что читают и вводят (поля, кнопки, суммы, таблицы, «Hof» в знаке); курсив — «перо» для заголовков, лент и вывесок. Цифры табличные. Шрифт хранится в самом Hof (woff2), внешних запросов нет.
- **Элементы — книга, нарисованная от руки:** всё, что обведено или подчёркнуто, нарисовано пером (`design/pen/`), кнопки и печати сообщений — нарисованные материалы (`design/generated/`). Как устроен каждый элемент — `design/screens.css` и холст.
- **Hof на компьютере** — боковое меню в виде синего знамени: Двор, службы, Приближённые (у Хозяина), внизу Мои покои и «Покинуть двор». На телефоне — верхняя полоса (знак → Двор, свеча → Мои покои), всё в одну колонку, сцена — полосой сверху. На холсте нарисованы все экраны телефона; формы Säckel, пустые состояния и ошибки 403/500 устроены как показанные образцы.
- **Карта двора и новые службы.** Полный список служб — в знамени, на телефоне — вывески под картой. Новая служба получает на карте свободную дверь; когда двери кончатся, карту перерисовывают с новыми домами, а раскладка экрана не меняется.
- **У сервиса своя шапка:** «← Двор», эмблема, название на ленте, вкладки — на компьютере поверх сцены сервиса, на телефоне компактно. У сервиса свой акцент (у Säckel — охра). Раскладка у каждого своя: в Säckel на компьютере список мешков слева и открытый мешок справа, а простые формы открываются в правой части; на телефоне это отдельные экраны.
- **Анимации, звуки и музыка** — только украшение. Без JS, звука и движения все функции Hof и Säckel работают; ни одно решение безопасности от JS не зависит.
  - Настройки — в localStorage этого устройства, у нового пользователя всё выключено. Системное «уменьшить движение» выключает анимации и в скриптах, и в CSS.
  - Код — `/static/fx-head.js` в `<head>` (ставит класс перехода до первой отрисовки) и `/static/fx.js`; Säckel подключает их по URL (раздел 2). Анимации включает класс `fx-on`, который ставит `fx-head.js`: если скрипты не загрузились, двор неподвижен.
  - Переходы между страницами — CSS (View Transitions, классы); вид перехода задаёт атрибут ссылки `data-fx`, флаги — в sessionStorage. Двигаются только `opacity`, `transform`, `clip-path` и кадры.
  - Звук — обычный `<audio>`, громкость — через Web Audio `GainNode` (на iPhone скрипт не меняет громкость `<audio>`). Записи под CC0, сведены заранее. Музыка — один список на все экраны, продолжается между страницами.
  - Граница: каждое действие — `<form method="post">` с кнопкой submit, каждый переход — `<a href>`. `fx.js` может только отложить штатную отправку на время анимации; сам он ничего не отправляет и не меняет поля, `action` и `method`. В хранилищах браузера — только настройки эффектов, позиция музыки и флаги переходов, никаких данных пользователя.
  - Доступность: функциональный текст — HTML (надписи на лентах и вывесках, кнопки, суммы); декоративные картинки — `alt=""` или `aria-hidden`; кот и сценки пустых страниц — не кнопки, а элементы с `aria-hidden` без фокуса; блок «Звуки и движение» без JS скрыт.
  - Подробности — длительности, варианты, громкости, кадры — в `design/fx.js`, `design/screens.css`, `design/sounds/mix.py` и `design/asset-prompt.txt`. Живой эталон — `design/preview/`.
- **Ассеты** лежат в `design/generated/`; что готово и что ещё генерировать — в `design/asset-prompt.txt`.
- **Эталон** — холст «Hof — экраны MVP» (https://claude.ai/artifact/ThWpky7k7NdU6nCFnq1gfF). Черновик стилей с него — `design/screens.css` (пути к картинкам локальные); доски и живой прототип собирает `design/canvas.py`, витрину анимаций для холста описывает `design/demo.css`.

## 7. Стек и зависимости

| Что | Выбор | Почему |
|---|---|---|
| Язык и runtime | TypeScript, Node.js ≥ 24.12 | Начиная с 24.12 встроенный type stripping стабилен: Node запускает `.ts` напрямую, без шага сборки, а типы проверяет `tsc --noEmit`. Минимальная версия фиксируется в `engines` в `package.json` и в базовом образе Docker |
| HTTP | `hono`, `@hono/node-server` | Маршруты, cookie, разбор форм, экранирующие шаблоны и тестовые запросы без сети. Мало «магии», нет собственных runtime-зависимостей |
| База | `pg` | Самый зрелый драйвер PostgreSQL для Node, пул соединений, параметризованные запросы |
| Пароли, токены | `node:crypto` | Argon2id, случайные токены, сравнение за постоянное время — без внешних пакетов |
| Тесты | `node:test` | Встроен в Node |
| Конфигурация | `node --env-file` | Встроено в Node, `dotenv` не нужен |
| Проверка входных данных | свои функции | Форм немного; явный разбор понятнее библиотеки схем |
| Dev-инструменты | `typescript`, `@types/node`, `@types/pg`, `eslint`, `typescript-eslint`, `prettier` | Typecheck, lint (включая правило границ модулей), форматирование |
| Пакетный менеджер | npm | Идёт вместе с Node; workspaces не нужны |

**TypeScript без сборки.** Node выполняет `.ts`, просто удаляя аннотации типов (type stripping). Поэтому в проекте используется только erasable-синтаксис TypeScript, то есть тот, который удаляется без преобразования кода. Конструкции, которым нужна трансформация во время выполнения, запрещены: `enum` (вместо него — union строковых литералов), `namespace` с кодом, parameter properties в конструкторах, `import x = require()`, декораторы, JSX. `tsconfig.json` настроен соответственно:

- `erasableSyntaxOnly` — компилятор сам отклоняет такие конструкции;
- `verbatimModuleSyntax` — импорты только типов пишутся как `import type`, иначе после удаления типов импорт сломается;
- `allowImportingTsExtensions` и `noEmit` — импорты указывают расширение `.ts`, а `tsc` только проверяет типы и ничего не генерирует;
- `module: nodenext` и `strict`.

Псевдонимы путей (`paths`) не используются: Node их не понимает.

Runtime-зависимостей три. Их сложнее всего убрать: `hono` используется во всех обработчиках, поэтому его замена затронет весь HTTP-код. `pg` используется только в функциях с SQL.

## 9. Развёртывание

- `compose.yaml` описывает `nginx`, `hof` и `postgres`. Наружу открыты только порты 80 и 443 у `nginx`. У `hof` и `postgres` нет `ports:`: до `hof` доходит только `nginx`. В `compose.dev.yaml` PostgreSQL публикуется только на `127.0.0.1` — опубликованные порты Docker обходят ufw.
- Образ `hof` собирается на самом сервере из репозитория. Registry и CI нет. Процесс в контейнере работает не от root.
- Конфигурация — в `.env`: домен (он нужен `nginx` и для сертификата, но не приложению), пароли БД, часовой пояс `TZ`, валюта `CURRENCY`. При старте сервер проверяет, что всё задано, и иначе завершается с понятным сообщением. Переменные передаются каждому сервису отдельно, а не общим `env_file`: `hof` получает только пароли ролей `hof_core` и `hof_saeckel`, пароль суперпользователя есть только у `postgres` для инициализации. Права на `.env` — 600.
- Обновление: резервная копия → `git pull` → `docker compose up -d --build`. Миграции применяются при старте.
- Резервная копия делается через `pg_dump` из контейнера `postgres`, восстановление — через `pg_restore`. Точные команды будут в README.
- **Способ доступа.** Hof всегда работает за HTTPS reverse proxy (`nginx`). Как пользователи до него добираются — по публичному домену, из локальной сети или через VPN (WireGuard, Tailscale), — зависит от конкретного сервера. Для Hof это не отдельные режимы. В приложении нет логики, зависящей от способа доступа: оно не знает своего домена и формирует только относительные ссылки. Варианты различаются только тем, откуда берётся сертификат, а `nginx` просто читает готовые файлы сертификата и ключа.
- **Reference deployment** и основная инструкция в README: публичный домен, HTTPS и сертификат Let's Encrypt. Обычным пользователям ничего не нужно настраивать, в том числе VPN.
- **nginx.** TLS 1.2 и 1.3 (профиль Mozilla intermediate), `server_tokens off`, `Strict-Transport-Security: max-age=31536000` без `includeSubDomains` и `preload`: за соседние поддомены владельца не решаем. Порт 80 отдаёт только `/.well-known/acme-challenge/`, остальное — 301 на HTTPS. Hof проксируется только для домена из `.env`; запрос с другим `Host` попадает в `default_server` и сбрасывается (`return 444`). `Host` передаётся таким, каким его прислал клиент (`$http_host`), `X-Real-IP` всегда перезаписывается своим `$remote_addr`; приложение `X-Forwarded-*` не читает и абсолютных URL не строит. Лимит попыток — раздел 4.5. Если перед `nginx` когда-нибудь встанет CDN или туннель, реальный IP настраивается в самом `nginx` (`real_ip`).
- **Сертификат** в reference deployment выпускает certbot на хосте из пакета дистрибутива, продлевает его systemd timer. Режим `--standalone` с хуками `docker compose stop nginx` и `docker compose start nginx`: несколько секунд простоя раз в ~60 дней, без отдельного контейнера. `nginx` читает `/etc/letsencrypt/live/<домен>/`, смонтированный только для чтения.
- Логи — stdout контейнеров (`docker compose logs`), json-file с ротацией: `max-size 10m`, `max-file 3`. Что писать в лог — раздел 4.10.

## 10. Разработка и проверки

- Разработка: `postgres` запускается из `compose.dev.yaml`, сервер — `node --env-file=.env --watch src/main.ts`.
- Тесты — интеграционные, против настоящего PostgreSQL: запросы к приложению через `app.request()`, без моков базы. В том числе есть тест, что роль Säckel не может прочитать схему `core`.
- После каждого milestone: `prettier --check`, `eslint`, `tsc --noEmit`, `node --test`, `docker compose build`. Всё вместе запускается одной командой `npm run check`.

## 11. Что намеренно не проектируем сейчас

- Установку и удаление приложений, манифесты, registry, динамическое подключение.
- Отдельные процессы для приложений, межсервисный протокол, сервисную аутентификацию.
- Подключение внешних продуктов (Vaultwarden и т. п.), поддомены, forward auth.
- Общие пакеты: UI-библиотеку, серверный kit, SDK. Сначала копирование, вынос только после второго приложения.
- Клиентский фреймворк, сборщик фронтенда, JSON API.
- Кэши, очереди, фоновые задачи, планировщик, отправку email.
- Несколько серверов, реплики, высокую доступность, Kubernetes.
- Метрики, трейсинг и платформу наблюдаемости: только логи в stdout.
- CI/CD, образы в registry, подпись релизов.
- Автоматические резервные копии по расписанию.
- В безопасности: CSRF-токены, JWT, Redis, блокировку по логину, 2FA, проверку по спискам утёкших паролей, CAPTCHA, fail2ban, продление сессий и «запомнить меня», список сессий, журнал действий, ключи идемпотентности, optimistic locking, перехеширование при входе, pepper, `Permissions-Policy`, COOP/COEP/CORP, `X-Frame-Options`, CORS, health endpoint.
- Как подключать второе приложение: решается, когда оно появится.
